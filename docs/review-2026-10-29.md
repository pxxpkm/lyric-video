## 1. 整體判斷

現有程式具備可運作的核心流程，純函式、主程序及畫面層已有分工，並有離線測試。未有證據支持「程式整體不能使用」的結論。不過，正式發布前應優先修正保存可靠性：使用者已經改好的時機、文字和外觀，有可能因離開畫面、舊快照或同時寫入而遺失。

其次是預覽與匯出的一致性，以及長片的時間邊界。測試通過數目不能取代這些使用者操作路徑的驗證。

## 3. 詳細發現與驗收條件

### R01：佇列重開會取回舊 session

**位置：** [queue.ts](../src/main/queue.ts) 的 `finishSaved`、`openJob`；[Preview.tsx](../src/renderer/src/Preview.tsx) 的初始化與自動儲存 effect；[matchLyrics.ts](../src/main/matchLyrics.ts) 的 `useCandidate`。

佇列完成時把 session 與 pick 放入記憶體。`openJob` 直接回傳快照，沒有從 projectPath 重新載入；使用者儲存時機、外觀或改選歌詞後，佇列快照沒有同步更新。預覽重新掛載後，又會自動寫入收到的舊時機、外觀和動畫。

**建議重現：** 從佇列打開工作，改延遲及字體，等待超過 200ms，返回並再次開啟同一工作；比較畫面與磁碟上的 timing、style、motion。對原本要選詞的工作，另驗證選詞後重開是否再次出現舊選詞畫面。

**影響：** 已儲存修改可能被回寫成舊值。這不是只顯示錯誤；畫面掛載觸發的保存會令錯誤持續到下次開啟。

**建議：** 佇列保留工作識別及 projectPath，開啟時讀取最新專案；選詞成功後更新工作狀態。不要把單純載入視為使用者修改。

**驗收：** 修改、返回、重開三次，畫面與檔案一致；已選詞工作不再要求重選；只開啟未編輯的專案不應覆蓋檔案。

### R02：自動儲存未在離開時完成

**位置：** [Preview.tsx](../src/renderer/src/Preview.tsx)，200ms 計時器、自動儲存呼叫及返回按鈕。

修改後 200ms 才發送 `saveTiming`；effect 清理只會清除計時器。若在窗口內返回，待儲存內容直接消失。儲存 Promise 沒有錯誤處理或可見狀態，無法知道修改是否已落盤。關閉程序亦缺少等待保存的協調流程。

**建議重現：** 調整字級後立即返回，重新讀取檔案；另用測試替身令保存拒絕，觀察是否有錯誤與重試入口。人手未必容易穩定命中 200ms，應以假的計時器測試。

**建議：** 使用明確的待保存／保存中／已保存／失敗狀態。返回、換專案及關閉前提交最後版本並等待確認；失敗時保留編輯內容及重試選項。不要只依賴 React 卸載清理完成非同步儲存。

**驗收：** 修改後立即返回仍保留內容；慢寫入時不提早宣稱已保存；拒絕寫入會提示，重試成功後狀態恢復。

### R03：同一專案的多次寫入互相爭用暫存檔

**位置：** [projectFile.ts](../src/main/projectFile.ts) 的 `saveProject`、`replaceFile`；[testClip.ts](../src/main/testClip.ts) 的 `savePreviewTiming`。

暫存路徑為 `${path}.${process.pid}.tmp`。同一程序對同一路徑發起兩次儲存會使用同一暫存檔；其中一次 rename 或錯誤清理會影響另一次。主程序 IPC 沒有對同一專案的完整讀取、修改、寫入流程排序。

**實測：** 對暫存專案同時呼叫 10 次 `saveProject`，觀察到 1 次成功、9 次 `ENOENT`，錯誤發生於將共用暫存檔 rename 到目的檔。這是合成並行負載，不能把 90% 當作日常操作失敗率。

**影響：** 慢寫入與後續自動保存重疊，或選詞更新與保存重疊時，會失敗或出現更新次序問題。R02 的無錯誤提示會令使用者不知情。

**建議：** 同一路徑的更新依次執行，並使用唯一暫存檔。需要涵蓋讀取、修改、寫入整個交易，避免只在最後寫檔排序但仍用舊資料覆蓋新資料。不同專案可獨立執行。

**驗收：** 並行更新不出現暫存檔碰撞；最後明確提交的版本成為最終結果；故障後專案仍是有效 JSON；不同欄位更新遵守明確的合併或版本衝突政策。

### R04：匯出目的地與檔案替換保護不足

**位置：** [ipc.ts](../src/main/ipc.ts) 的 `export:video`；[exportVideo.ts](../src/main/exportVideo.ts) 的 `exportProject`；[exportName.ts](../src/core/exportName.ts) 的 `exportPartPath`。

儲存對話框選定的 outPath 沒有與 mediaPath 比對。轉碼成功後先 `rm(outPath)`，再 `rename(part, outPath)`。使用者若選回來源 MP4，來源便可能被刪除及替換；若目的檔刪除後 rename 失敗，原有成片已不在原位置。暫存檔名亦是可預測的 `<名稱>.part.mp4`，配合 ffmpeg `-y`，會有碰撞風險。

**驗證界線：** 本次沒有刪除或覆蓋真實影片。Windows 檔案鎖可能令某些情況先失敗，不能視為穩定的來源保護。

**建議：** 正規化並檢查來源、目的和暫存路徑；考慮 Windows 大小寫及指向同一實際檔案的情況。使用唯一暫存檔；替換既有成片時採用可回復策略，並確認成片有效才完成替換。

**驗收：** 輸出到來源路徑被拒絕；模擬 rename 失敗後原有成片仍可恢復；碰到既有 `.part.mp4` 不得覆蓋無關檔案。破壞性案例只用可丟棄的測試素材。

### R05：譯文開關只處理原始資料

**位置：** [Preview.tsx](../src/renderer/src/Preview.tsx) 的 linesRef 與 `exportBody`；[lyrics.ts](../src/core/lyrics.ts) 的 `applyEdits`；[ass.ts](../src/core/ass.ts) 的 `buildKaraokeAss`。

showTrans 為 false 時先清空基礎歌詞的譯文，但後續 `applyEdits` 又從 timing.trans 或 timing.added 加回譯文。開關沒有在完成所有編輯後統一生效。

**實測：** 基礎歌詞沒有譯文，但 timing.trans 放入「隱藏後仍出現的譯文」，生成的 ASS 仍包含該文字。這重現了匯出資料處理路徑；預覽亦使用相同的編輯合併順序。

**建議：** 先產生完整有效歌詞，再根據顯示設定決定是否渲染譯文；保存的譯文內容應保留，避免關閉顯示變成刪除資料。

**驗收：** 原始、修改及新增句子的譯文都遵守開關；再次開啟後內容恢復；預覽、ASS、MP4 結果一致。

### R06：偏移限制誤用為歌詞時間上限

**位置：** [timing.ts](../src/core/timing.ts) 的 `MAX_MS = 300000`；[lyrics.ts](../src/core/lyrics.ts) 的 `applyEdits`、`setEffectiveTime`。

300 秒原本用作偏移量界限，但新增歌詞的絕對時間及設定有效時間也使用該上限。這不代表五分鐘之後所有原有歌詞都不能播放；問題集中於相關新增及時間編輯路徑。

**實測：** timing.added 中 atMs 為 360000 的句子，經 `applyEdits` 後 timeMs 變成 300000。

**建議：** 分離偏移量上限和曲內時間範圍。時間位置依媒體長度及編輯政策判斷，不能默默截到五分鐘。12 分鐘歌曲不參與時長匹配的規則，不應變成編輯時長限制。

**驗收：** 在 4:59、5:00、5:01、6:00 及 12:00 插入／修改時間，不會意外移位；保存及重開後一致；輸出字幕時間亦一致。

### R07：正延遲之前的時間被當作零秒

**位置：** [preview.ts](../src/core/preview.ts) 的 `lyricClockMs`、`mediaMsForLyric`；[ass.ts](../src/core/ass.ts) 的事件時間計算。

預覽計算 `(mediaMs - offsetMs) * rate` 後以 `Math.max(0, ...)` 截斷負值。當歌曲有零秒歌詞而 offset 為正，實際尚未到起點的時間卻被當成歌詞零秒。

**實測：** 零秒歌詞、offset 5000、媒體時間 0，`previewFrame` 已返回該句；ASS 同一句則從 `0:00:05.00` 開始。畫面最初的淡入可能掩蓋部分現象，但核心的啟用狀態已不一致。

**建議：** 明確處理「尚未到歌詞起點」；檢查負時間、淡入及逐字進度，避免只改讀數而保留錯誤的啟用狀態。

**驗收：** 零秒歌詞延遲五秒後，前五秒預覽不應啟用該句；開始顯示及逐字進度與輸出相符。另測正負 offset 及 rate 0.85／1／1.20。

### R08：新來源失敗後沿用舊來源

**位置：** [App.tsx](../src/renderer/src/App.tsx) 的 `readUrl`、`readFile`、`applyDraft`、`save`。

只有探測成功時才更換 source 與 draft。失敗分支更新錯誤訊息，沒有使舊來源失效；建立專案按鈕只看 busy 與 source 是否存在。

**重現步驟：** 成功讀取 A，改輸入無效 B 並讀取，等待失敗後按建立專案；後端仍可能處理 A。即使只是修改網址而未重新讀取，顯示文字與已解析來源也可能不同。

**建議：** 清楚分開輸入中的來源和已確認來源；內容變更時令舊探測結果失效，或明確顯示「目前將匯入 A」。失敗不能令 UI 暗示 B 可用。

**驗收：** A 成功、B 失敗後不能無提示地建立 A；網址、來源、標題及時長始終屬於同一次確認結果。

### R09：busy 與畫面生命週期未完整約束請求

**位置：** [App.tsx](../src/renderer/src/App.tsx) 的 onDrop、選詞非同步回呼；[PickSong.tsx](../src/renderer/src/PickSong.tsx) 的雙擊與返回按鈕。

拖放未檢查 busy；選詞結果的雙擊也未停用。使用者可在舊請求仍執行時提交新請求或返回，回呼仍可能呼叫 showMatch 並改變畫面。單一布林 busy 無法辨識哪個請求擁有目前畫面。

**建議重現：** 用可控制完成順序的測試替身模擬 A 慢、B 快，連續拖入兩個檔；另外在搜尋時返回，再讓搜尋完成，確認是否被帶回選詞頁。這些 GUI 時序本次未實際逐項操作。

**建議：** 對所有入口一致處理忙碌狀態；加入請求識別及過期回應檢查。返回後停止接受該畫面的結果；可取消的操作應一併取消。

**驗收：** 舊結果不能覆蓋新選擇；返回後不被舊回呼跳頁；同一選詞動作最多提交一次；錯誤能在目前可見畫面呈現。

### R10：外部程序無取消及應用層逾時

**位置：** [media.ts](../src/main/media.ts) 的 `runCommand`；[queue.ts](../src/main/queue.ts) 的 `pump`。

runCommand 等到 error／close 才結束，沒有取消介面、應用層時間限制或輸出大小限制。若外部程序長時間不退出，該工作保持 running，後續佇列工作不會開始。歌詞 HTTP 請求已有八秒 timeout，這項問題主要針對外部程序，不能概括為全程式沒有逾時。

**建議：** 探測、下載、轉碼採不同逾時政策；下載與轉碼提供取消；終止時處理 Windows 子程序及部分產物。錯誤輸出保留有上限的尾段，不應無限累積。

**驗收：** 用可控制的測試子程序模擬不退出、大量輸出和錯誤結束；取消後工作釋放，下一工作能開始，診斷仍保留必要訊息。

### R11：既有專案缺少重新開啟入口

**位置：** [App.tsx](../src/renderer/src/App.tsx) 的 savedPath／jobs；[queue.ts](../src/main/queue.ts) 的記憶體 jobs。

有 project.json 保存機制，但目前 UI 依賴本次程序的 savedPath 及佇列。重啟後缺少開啟專案或最近專案入口。檔案不一定遺失，但一般使用者難以續做。

**建議：** 增加開啟專案和最近專案入口；來源媒體搬走時可重新定位。本機匯入目前保存原始媒體路徑，不是把來源複製入 studio-data，因此恢復流程必須考慮失效路徑。

**驗收：** 關閉再開能恢復 timing、style、motion；來源不見時提示重新定位，不應要求重做所有歌詞修改。

### 核心重現片段

以下摘錄已執行檢查的關鍵輸入；模組路徑以專案根目錄為基準，需透過專案 TypeScript 測試／建置工具執行。保存案例只能使用新建的暫存資料夾。

```ts
// R05：對應 exportBody 在 showTrans=false 時只清除基礎譯文。
const line = lyricLine(1000, "原文");
const t = defaultTiming();
t.trans = { [lineKey(line)]: "隱藏後仍出現的譯文" };
buildKaraokeAss([line], t).includes("隱藏後仍出現的譯文"); // 實測 true

// R06
const added = defaultTiming();
added.added = [{ atMs: 360000, text: "六分鐘插句", id: "a" }];
applyEdits([], added)[0].timeMs; // 實測 300000

// R07
const delay = defaultTiming();
delay.offsetMs = 5000;
previewFrame([lyricLine(0, "零秒歌詞")], lyricClockMs(0, 5000, 1), delay).text;
// 實測「零秒歌詞」；同一輸入的 ASS Dialogue 起點為 0:00:05.00。

// R03：tempPath 必須指向可丟棄的測試專案，不能使用使用者專案。
const results = await Promise.allSettled(Array.from({ length: 10 }, (_, i) => {
  const p = exampleProject();
  p.identity.title = `save${i}`;
  return saveProject(tempPath, p);
}));
// 本次觀察：1 fulfilled，9 rejected；並行完成次序不保證每次相同。
```

所需函式分別位於 core/lyrics、core/timing、core/ass、core/preview、core/project 及 main/projectFile。檢查當時使用暫存 TypeScript 程式經既有 esbuild 打包執行；沒有把額外測試加入正式套件，亦沒有停用現有測試。
